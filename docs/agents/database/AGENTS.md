# 数据库 Agent 专项规范

先读取仓库根目录 `AGENTS.md`；本文件由根入口按任务显式加载，不依赖 docs 目录的自动发现。本文约束相关业务源码，历史记录不是现行指令。

## 八、数据库 Agent 职责与验收

- 首先执行只读数据库审计，维护未使用对象台账。
- 同时核对 ORM 与真实库的表、列、约束、索引及数据分布，不能只根据模型设计。
- 结构直接表达业务语义，避免同一概念有多个可独立变化的状态。
- 字段明确类型、长度或精度、默认值、可空性、空值含义、单位、时区和中文说明。
- 与后端共同确定唯一约束、外键、事务、并发和幂等依据，按真实查询设计索引。
- 结构变化提供版本迁移，说明前置版本、顺序、失败处理、回退和备份恢复。
- 不以 ORM 自动建表代替升级迁移，不允许多个 Agent 各自维护建表逻辑。
- 原库只读；迁移和分析使用副本或独立测试库，统计和样本脱敏。
- 历史数据默认不回填、不重算、不覆盖。经授权迁移记录映射、异常处理、前后数量、状态分布和校验结果。
- 不能处理的数据保留并报告，不删除数据使迁移通过。

数据库交付须证明新库初始化、目标旧版本升级、约束有效、关键查询性能和失败恢复。SQL 成功不等于迁移验收通过。

数据库 Agent 的最小开工顺序：读取 docs/project-history.md 中相关审计结果 → 用只读方式复核任务涉及对象 → 追踪模型、动态 SQL、编译模块调用和外部消费者 → 与后端确认目标语义和访问模式 → 设计结构及索引 → 编写版本迁移 → 在副本演练 → 核对前后数量和关键分布 → 演练恢复 → 更新 docs/project-history.md 台账并交给主 Agent。

### 8.1 数据库结构变更的唯一来源

任何表、字段、索引、约束、视图、触发器和初始化数据变更，都必须先判断项目采用哪一种权威建库方式，并遵守对应规则：

1. 程序代码、迁移框架或脚本负责建库时，变更必须写入该权威代码或正式迁移脚本，并由应用或迁移执行器按版本运行。禁止另存增量 SQL 或临时 SQL 文件，也禁止只修改 ORM 而遗漏升级路径。
2. SQL 文件负责建库时，只维护一份能够从空数据库创建当前完整结构的全量 SQL。表结构变化后直接更新这份全量 SQL，确保新安装得到最终结构；禁止为每次变化新增散落的增量 SQL 文件。
3. SQL 文件管理的新库初始化与历史库升级必须同时成立。全量 SQL 负责创建新库；已运行实例的无损升级由程序内或正式脚本内的版本化迁移逻辑负责，迁移版本、顺序和执行结果持久化记录。不得靠人工执行零散 ALTER SQL 完成生产升级。
4. 正式迁移必须可判定前置版本、可重复安全检查、使用事务或明确补偿、迁移数据后再收紧约束，并提供失败恢复方案。数据库不支持事务 DDL 时，逐步设计可恢复检查点。
5. 删除、改名、拆分、合并字段或改变类型时，采用“新增结构 → 双读或回填验证 → 切换读写 → 删除旧结构”的兼容过程；未核对历史数据和所有消费者前，不执行破坏性步骤。
6. 每次结构变更都要验证两条路径：空库使用权威脚本可一次创建成功；至少一个受支持的旧版本数据库可无损升级到当前版本。两条路径的最终结构必须一致，并核对表数、字段、约束、索引、数据量和关键分布。
7. 仅用于诊断的查询在数据库客户端或 dbx MCP 会话中执行，不保存到项目目录。确需成为长期回归资产时，转化为正式测试、迁移检查或运维命令，并放入项目既定位置。

### 8.2 PostgreSQL 与 MySQL 的本地 Docker 调试

目标数据库为 PostgreSQL 或 MySQL 时，可以在本机 Docker 启动隔离容器进行开发、建库、迁移和兼容性验证，并优先使用 dbx MCP 执行数据库创建、读取、修改和结果回查。

- 容器镜像版本必须与目标部署版本一致；未确定目标版本时不得自行选用 latest 作为兼容性结论。
- 使用任务专属容器名、数据库、用户、端口、网络和持久卷，避免连接已有业务容器。启动前检查端口和同名资源，禁止删除或复用归属不明的容器和卷。
- 调试账号、密码和连接串只放在运行时环境或系统临时配置中，不写入任何规范、源码、SQL、日志、截图或提交。测试账号不得复用生产凭据。
- 使用 dbx MCP 前先列出或确认连接信息，核对数据库类型、主机、端口、数据库名、schema 和当前用户。所有写操作只对本地测试容器执行；目标不明确时只读检查并停止写入。
- 建库和结构变更通过项目权威建库方式执行，dbx MCP 用于运行、查询、核对和必要的测试数据操作；不得借 dbx MCP 手工修改结构后不回写权威脚本或迁移代码。
- 每次写入后用 dbx MCP 重新读取结构和数据验证结果。迁移验证至少包含空库初始化、旧版本升级、重复执行防护、失败恢复和关键查询。
- 如果当前环境没有 dbx MCP 或连接失败，先诊断 MCP 是否安装、数据库驱动、连接配置、Docker 网络和容器健康状态。仍不可用时明确报告阻塞，不把未经 dbx 回查的结果写成已验证。
- Docker Compose、Dockerfile 或数据库初始化配置只有在它们属于正式项目运行方式时才进入仓库；纯调试用容器参数和配置保存在系统临时目录。
- 调试结束后删除本任务创建的测试容器、临时网络和临时卷，或明确保留原因和所有者。删除前逐项核对名称和归属，不影响其他任务及用户数据。

### 8.3 数据库审计与未使用对象台账

涉及旧库及历史数据的任务先核查已有审计；缺少证据时，由任务负责人对已授权副本执行只读审计，不重复运行旧版入口：

1. 导出表、字段、类型、默认值、非空、主外键、唯一约束、索引和触发器。
2. 统计各表行数、关键字段空值和重复值、状态枚举、时间范围及孤立关联，输出必须脱敏。
3. 搜索旧模型、查询、写入、任务、迁移和配置对每个表、字段和索引的引用。
4. 将对象分为确认使用、仅迁移使用、疑似未使用、证据不足、确认废弃。不能仅凭文本搜索不到判定废弃，还要考虑动态 SQL、ORM 反射、编译模块和外部工具。
5. 在docs/project-history.md 的数据库未使用对象台账记录对象、证据、可能语义、相关功能、风险、下次核查触发点和决定。
6. Agent 开发到相关功能时重新检查对应对象，结合对标页面、数据分布和业务调用推导逻辑，将新证据反馈主 Agent 更新台账。
7. 未经授权和迁移验证，不删除疑似未使用对象，不回填、不重算、不覆盖历史数据。
