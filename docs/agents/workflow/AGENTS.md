# 协作与交付 Agent 专项规范

先读取仓库根目录 `AGENTS.md`；本文件由根入口按任务显式加载，不依赖 docs 目录的自动发现。本文约束相关业务源码，历史记录不是现行指令。

## 四、所有 Agent 的强制工作流程

### 4.1 开始前

1. 完整阅读本文件，确认项目事实、当前决策、自身职责和修改边界。
2. 检查 Git 状态及已有文件，不覆盖无关改动。
3. 按任务定位对标页面、旧源码入口、数据库对象、外部模块和消费者。
4. 写清业务目标、范围、排除项、依赖、契约版本和验收场景。
5. 将证据标为已确认、合理推断或未验证；项目可查内容先自行查明。
6. 技术栈、重建范围、历史数据或兼容策略未确定且影响结果时，由主 Agent 统一决策或询问用户。

每个执行 Agent 开始前必须能回答以下问题，否则继续勘察，不进入编码：用户最终看到或调用什么结果；旧功能证据在哪里；本任务的权威业务规则在哪里；会读写哪些表、字段、接口和文件；依赖哪个契约版本；如何验证正常、失败及恢复场景；会不会产生外部副作用或历史数据变化。

### 4.2 实现中

- 按可独立验收的业务切片推进，例如“创建订阅并在列表正确显示”，不能只拆成建表、写接口、画页面等互不验收的技术碎片。
- 一个业务规则只有一个权威实现。HTTP、定时任务、消息入口、列表和详情复用同一服务规则。
- 同一概念在数据库、后端、前端和 Apifox 中使用一致名称、类型、枚举、单位、时区和空值语义。
- 保持修改范围与任务一致；只治理影响当前工作的结构问题，不做无关重构。
- 同一文件同一时间只有一个写入负责人。跨 Agent 修改先说明接口、字段、消费者、兼容和迁移影响，由主 Agent 协调。
- 不用前端兜底掩盖后端状态错误，不用后端兼容分支掩盖数据库语义错误，不用删数据绕过约束错误。

### 4.3 临时文件和目录

#### 4.3.1 新文件和新目录创建审批规则

- Agent 不得因为个人习惯、通用工作流、技能默认步骤或“方便记录过程”而在项目目录新增文件或目录。任何新路径都必须同时满足以下条件：属于用户当前任务的明确交付物；创建位置符合本文件约定；由主 Agent 在任务提示、交接消息或明确续指令中批准；并能说明负责人、用途、生命周期和验收方式。
- 未经主 Agent 明确批准，禁止在仓库根目录或现有模块下新增 `docs/`、`docs/agents/`、`docs/architecture/`、`notes/`、`specs/`、`design/`、`tmp/`、`temp/`、`debug/`、`screenshots/`、`artifacts/` 等目录，也禁止新增任务说明、设计稿、过程记录、交接文档、审查报告、一次性脚本和个人笔记。根目录AGENTS.md维护入口，专项规则只维护在其链接的docs规范中，历史证据维护在docs/project-history.md；通用技能要求与本条冲突时，以本项目规则为准。
- 需要参考外部仓库时，克隆目录必须放到操作系统临时目录或工具隔离目录，且任务结束前清理；不得把参考仓库、依赖源码、浏览器缓存或下载包放进项目目录。构建、测试、截图和导出工具若默认向项目目录写入，必须在执行前改到临时目录或正式且已批准的模块目录。
- 修改已有文件不等于可以顺手创建配套文件。新增测试、迁移、配置模板、接口文档或产品资产时，必须先确认它是本任务的正式长期交付物，并放入已有规范目录；不能用“以后可能有用”作为创建理由。
- 如果发现项目中已经存在来源不明的新文件或目录，Agent 只能只读盘点、报告路径和影响，不得擅自删除、移动、重命名或覆盖；由主 Agent 与用户确认归属后再处理。完成任务前必须检查 `git status --short` 和目录清单，确认没有本次 Agent 未声明的新增路径。
- 每个 Agent 的任务提示和完成回报必须写明“允许创建的路径”和“明确禁止创建的路径”。未列入允许范围的路径默认禁止创建；跨目录修改必须由主 Agent 重新授权。

- 禁止把调试脚本、抓包、临时截图、数据库副本、导出数据、浏览器缓存、安装包、构建试验、一次性代码或个人笔记保存到项目目录。
- 禁止在项目目录生成或保存临时 SQL、一次性 SQL、手工修复 SQL、调试 SQL、按日期或需求命名的增量 SQL。无论文件是否准备提交，只要不是项目正式、唯一且长期维护的数据库来源，就不得写入仓库。
- 临时产物放入操作系统临时目录或工具隔离目录，使用可识别任务的专用名称。不得集中堆放到仓库内的 tmp、temp、debug、screenshots 等目录。
- 正式测试夹具、迁移样本和产品资产只有在确属长期维护内容时才能入库，并放到所属模块的规范目录且被代码或测试实际引用。
- 命令产生缓存或构建产物后检查 Git 状态和目录结构；无长期价值的产物在任务结束前安全清理，不删除用户原有或归属不明文件。
- 不在仓库保存数据库副本和真实凭据，原始 lady.db 保持只读。

### 4.4 公共封装

- 后端 HTTP 请求、采集解析、重试超时、代理、队列任务、定时调度、日志、错误映射、配置、认证、数据库事务和第三方客户端统一封装。
- 前端请求客户端、API 模块、认证状态、错误处理、分页、图片预览、图片加载兜底、骨架屏、空状态、确认交互、通知反馈和表单基础能力统一封装。
- 新增前先搜索已有实现；已有能力满足时复用，不能满足时扩展公共能力并验证消费者，不在页面或服务复制近似实现。
- 同一逻辑已出现两处且第三处需求明确时，应在第三处实现前抽取公共封装。单次、简单且无复用价值的逻辑不为形式制造抽象。
- 公共封装须有稳定接口、明确错误语义和核心测试；禁止只转发调用、没有降低重复或耦合的空壳层。

### 4.5 注释标准

- 前后端新增或修改的类、结构体、接口、公共组件、公共方法、导出函数和关键业务方法必须写说明注释。
- 注释说明职责、关键约束、输入输出或副作用，不复述语法。状态转换、并发、幂等、兼容逻辑和非常规算法说明原因。
- Go 导出标识符使用符合 GoDoc 的注释；TypeScript/JavaScript 公共 API 使用项目约定的 TSDoc/JSDoc；迁移说明数据意图和回退限制。
- 注释、实现和契约同步更新。过期注释视为缺陷，禁止保留误导内容或大段注释掉的旧代码。

### 4.6 完成前

1. 执行与风险匹配的语法、类型、单元、集成、构建和业务验证。
2. 核对与任务相关的正常、空值、异常、重复、并发、超时、重试、取消和恢复场景。
3. 检查 Git diff 和状态，确认没有秘密、调试代码、临时产物和无关修改。
4. API 修改完成 Apifox 同步并回读；数据库修改完成迁移演练和数据核对；UI 修改完成浏览器实际验收。
5. 汇报实际行为、修改范围、验证命令与结果、历史数据影响、未验证事项和剩余风险。

### 4.7 Git 源码仓库与构建产物边界

Git 仓库用于保存源码和可重复构建所需的长期资产，不用于保存本地打包结果或发布包。

- 必须提交：前后端源码、测试源码、依赖清单及锁文件、构建配置、Dockerfile、正式 Docker Compose 配置、配置模板、权威建库脚本或正式迁移、代码生成配置、必要文档和长期维护的产品资源。
- 必须忽略：前后端打包目录、编译后的可执行文件、安装包、压缩包、镜像导出文件、node_modules、测试覆盖率和报告、缓存、日志、临时文件、本地数据库、IDE 配置、操作系统文件、本地环境变量文件及密钥。
- 常见的 dist、build、out、bin、coverage、target 和临时发布目录均默认属于构建产物；如果所用工具使用其他输出目录，建立工程时同步加入根目录 .gitignore。
- 不得为了提交方便把构建产物复制到源码目录。打包命令必须输出到明确且被忽略的目录，并且可通过已提交的源码、锁文件和构建配置重新生成。
- 自动生成的源码默认由构建流程重新生成。只有当目标工具链无法在构建时生成、生成结果属于公开接口或项目已有明确的入库约定时，才允许提交；必须同时提交生成源和生成命令，并在审查中核对一致性。
- vendor 或同类依赖源码目录是否提交由项目依赖策略统一决定，不能因其是目录便一律忽略；一旦选择 vendoring，必须由依赖工具生成并保持版本一致。
- 创建或调整工程结构时同步维护根目录 .gitignore。提交前使用 Git 状态和忽略规则检查，确认已跟踪的是源码和构建定义，打包产物、真实配置、凭据及临时文件均未进入暂存区。

### 4.8 Docker 发布镜像边界

Docker 发布使用多阶段构建或等效的“构建环境与运行环境分离”流程。构建阶段可以临时复制源码并安装编译依赖；最终运行镜像禁止包含源码、测试、版本库和编译工具，只保留程序运行必需的打包产物。

- Go 后端最终镜像只复制编译后的服务可执行文件，以及运行必需的正式迁移、配置模板、证书、时区数据和静态资源；不得复制 .go 源码、测试源码、Go 编译器、模块下载缓存和构建缓存。
- 前端最终镜像只复制正式构建输出的静态文件到 Web 服务器目录；不得包含 TypeScript、JavaScript 源文件、Vue/React 源码、node_modules、测试、开发服务器和包管理器缓存。生产 source map 默认不发布，确需发布时必须有调试与源码暴露风险决策。
- 如果前后端合并为单一镜像，只复制后端可执行文件和前端静态产物等运行资源，不把整个工作区复制到最终阶段。
- 最终镜像可包含应用启动时确实需要执行的正式版本迁移，但不得包含调试 SQL、临时数据库工具、数据库副本或历史迁移试验文件。
- 根目录 .dockerignore 必须排除 .git、编辑器文件、本地环境文件、密钥、日志、数据库、临时目录、测试报告、本地依赖缓存和与构建无关的打包产物。不得错误排除构建阶段需要的源码、锁文件、构建配置或正式迁移。
- Dockerfile 不使用无边界的 COPY 将整个仓库直接带入最终阶段。构建阶段也应按依赖清单、源码和资源分层复制，以利用缓存并缩小上下文。
- 最终镜像使用非 root 用户运行；不安装 shell、编译器、包管理器和调试工具，除非运行时有明确且经过审查的必要性。
- 镜像标签使用明确版本或不可变提交标识，不以 latest 作为唯一可追溯版本。构建产物通过 CI、制品库或容器仓库发布，不回写 Git 源码仓库。
- 发布验收必须检查镜像文件清单和层历史，确认不存在源码、.git、测试、开发依赖、构建缓存、真实配置或密钥；随后用最终镜像完成启动、健康检查、配置注入、静态资源和适用迁移验证。

## 五、主 Agent 职责

- 在项目初期完成源码、对标系统、数据库和运行环境勘察，维护docs/project-history.md。
- 将需求拆成可交付业务切片，为任务指定负责人、允许范围、契约版本、依赖和验收条件。
- 维护参照与差异、业务与数据字典、API 契约三项共同依据；当前规则写入对应专项规范、历史证据记录在docs/project-history.md，详细 OpenAPI 和迁移文件随代码存放。
- 统一跨端命名、状态、兼容策略和错误模型，解决前端、后端、数据库冲突。
- 指定共享配置、依赖锁文件、生成产物和集成记录的唯一写入负责人。
- 区分已实现、已测试、已联调、已验收，不能用执行 Agent 的自报完成代替集成验收。
- 复核代码、契约、数据和运行证据，最终交付结论由主 Agent 给出。

主 Agent 每次派发任务至少提供：任务编号和业务目标、角色与负责人、旧功能证据、目标差异、包含及排除范围、契约版本、允许修改的文件或模块、数据库对象、上游依赖、下游消费者、并行条件、正常及异常验收、外部操作授权、历史数据授权和最终交付物。缺少其中会改变实现结果的内容时，先补证据或决策。

### 5.1 并行任务规则

- 同类、相同功能或重复操作的独立任务达到 3 个以上时，主 Agent 必须优先批量并行处理；用户和当前环境允许多 Agent 时可多任务分派，禁止无必要逐个串行。
- 并行任务必须没有未完成输入依赖、不写同一文件、不改同一数据库对象、不竞争同一外部状态，并有清晰输入与验收标准。
- 共享契约、公共封装和数据库迁移等上游先完成或冻结版本，再并行消费者。存在顺序依赖时必须串行，不能为数量强行并行。
- 并行结束后由主 Agent 统一检查风格、重复实现、契约一致性、冲突、构建、测试和真实业务流程，不直接拼接结果后宣称完成。
- 当前环境或上级指令禁止子 Agent 时，使用工具级并行或批处理完成独立读取、检查和验证，不违反上级限制。

### 5.2 数据库审计与规范交接

涉及旧库、仓储或迁移时，读取[数据库规范](../database/AGENTS.md)中的审计流程；不复制维护第二套审计要求。初次审计已经完成的对象按任务复核历史台账，不能自动重跑迁移或恢复历史授权。

派发、规范更新通知、执行Agent自行读取及交付复核，严格执行[根入口](../../../AGENTS.md)的“Agent 开工、派发、更新与交付”。每次任务提示必须包含实际规范路径及章节、允许创建/修改路径、禁止范围、契约版本及验证条件；现有角色章节不是自动授权。

## 九、审查 Agent 职责与验收

审查 Agent 独立检查交付是否满足用户目标、本文件规则和冻结契约，不替执行 Agent补做未授权实现，也不只检查代码风格。

- 开始前读取本文件、任务输入、差异和实际 diff，不依赖执行 Agent 的总结作为事实。
- 核对业务正确性、状态语义、数据一致性、权限和敏感信息、并发与幂等、错误处理、迁移安全、API 契约、公共封装和注释。
- 前端审查必须查看浏览器验收证据；API 审查必须查看 Apifox 回读证据；数据库审查必须查看副本迁移和数据核对结果。
- 发现问题时写明严重度、触发条件、具体位置、影响和可验证的修复标准。无法证明的问题标为疑问，不伪装成已确认缺陷。
- 修复后重新检查相关 diff 和验证结果。审查通过只代表其职责范围通过，最终验收仍由主 Agent 完成。

## 十、契约、所有权和交接

- 参照与差异由主 Agent 维护，所有 Agent 补证据。
- 业务和状态字典由后端与数据库提出、主 Agent 定稿、前端消费。
- API 契约由后端维护、前端和数据库评审，Apifox 保存最终协作定义。
- 数据结构和迁移由数据库 Agent 维护，后端评审查询和写入需求。
- 页面、组件和前端调用层由前端 Agent 维护。

契约绑定仓库提交或显式修订号，不能只写“最新版”。字段或状态变更说明原因、消费者、兼容方式、迁移影响和验收场景。

交接顺序：参照核实 → 契约确定 → 分工实现 → 真实联调 → 主 Agent 验收。持久化联调必须使用真实迁移结果；前端真实联调必须使用真实 API。

### 10.1 任务交付回报格式

每个 Agent 完成任务时统一报告：关联任务和契约版本；实际完成行为；修改文件和范围；接口或数据变化；验证环境、命令、场景和结果；浏览器、Apifox、迁移或第三方证据；历史数据影响；临时数据和临时文件清理结果；未验证内容、联调依赖和剩余风险；当前状态属于已实现、已测试还是已联调。

## 十一、测试与完成标准

- 测试强度与风险匹配，不为低影响可逆改动编写只复刻实现的测试。
- 订阅和任务按适用场景验证重复提交、并发、取消后执行、超时、回查、重试和重启恢复。
- 前端验证真实浏览器，后端验证业务与适配器，数据库验证迁移和数据，主 Agent 验证跨端链路。
- 测试数据使用独立库、事务回滚或明确清理，并核对清理结果。
- 区分静态检查、业务测试、跨端联调、真实第三方验证；四类证据不能互相替代。
- 无真实环境时可交付模拟测试但标记未验证；若真实验证是验收条件，任务不得标为已验收。
- 完成报告包含实际行为、修改文件、接口或数据变化、验证环境和命令、结果、历史数据影响、临时数据清理、未验证内容和风险。
