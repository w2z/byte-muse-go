# 后端 Agent 专项规范

先读取仓库根目录 `AGENTS.md`；本文件由根入口按任务显式加载，不依赖 docs 目录的自动发现。本文约束相关业务源码，历史记录不是现行指令。

## 七、后端 Agent 职责与验收

- 开始前阅读相关路由、服务、调度、模型、配置、第三方适配和数据库台账。
- 业务规则集中在服务层，HTTP、任务和消息入口复用；状态转换明确触发条件、前置状态、执行者、事务边界和失败结果。
- 区分请求受理、任务创建、资源添加、下载完成和媒体入库，不能沿用含糊的旧 COMPLETE。
- 统一封装 HTTP 请求、采集、解析、代理、限速、重试、队列、调度、日志、配置、认证、错误和第三方客户端。
- 对副作用设计幂等键、并发控制、超时、重试、补偿和结果回查。超时不能直接视为未执行并盲目重试。
- 输入校验、认证、授权和敏感信息保护由后端完整执行，不依赖前端。
- 持久化遵循数据库设计，结构变化用版本迁移，禁止启动时静默修表。
- 验证正常和异常流程；第三方 HTTP 成功不等于业务成功，按能力回查结果。

### 7.1 开放 API 与 Apifox

新增、修改或删除开放 API 时，代码、测试、OpenAPI 契约和 Apifox 必须同任务交付，并使用 apifox-new-mcp 同步：

1. 以最终代码确认路径、方法、鉴权、参数、请求体、响应、错误、枚举、空值和真实示例。
2. 先获取可访问项目与项目结构，确认项目 ID、分支、模块和目录，不编造 ID。
3. 按 URL 和 HTTP 方法搜索现有节点，不依赖记忆中的接口 ID。
4. 已有接口更新原节点；新增接口放入正确目录；删除前确认属于本任务、确已废弃且无消费者。
5. 新增或修改字段填写中文说明、类型、枚举、必填性、空值含义和场景。
6. 环境基址已含 /api/ 时，接口路径不再添加 /api，避免 /api/api/。
7. 写入后重新读取详情，核对 URL、方法、目录、参数、响应示例和说明。
8. Apifox 不可用、项目不明或权限不足时先诊断工具、连接和项目信息；仍无法恢复则报告阻塞，API 任务不能标为完整交付。

后端 Agent 的最小开工顺序：定位所有旧调用入口 → 核实状态和副作用 → 查看数据库台账 → 搜索现有公共服务与适配器 → 先确定或更新契约 → 实现权威服务 → 接入 HTTP、任务或消息入口 → 验证幂等和失败语义 → 更新 OpenAPI 和 Apifox → 回读核对后交给主 Agent 联调。

## 已确认约束

- 日志已接入持久化Store，不能再按早期500条内存环形缓冲设计；修改前核查internal/logging与数据库日志仓储。
